## 1. 目的と前提

### 1.1 目的
本校のスプレッドシートをそのままアプリ化することではない。本校の形式は「ある1校の実例」にすぎない。
目的は、校種・規模・運営形態の異なる多くの学校が、自校の行事予定表の形を**コード変更なしに設定だけで再現できる**、汎用性の極めて高い行事予定管理アプリを作ることである。

### 1.2 調査から確定した事実
- 25件すべてに共通する項目は「日付（日＋曜日）」と「その日の出来事を書く自由記述欄」の2つだけだった。
- 給食列すら無い学校がある。下校時刻・時限・日直は過半数で独立列を持たない。
- 変動は「列の有無」だけではない。次の4つの構造的変動がある。
  1. 同じ概念が 独立列／行事欄への埋め込み／脚注・凡例／別表・別PDF の4形態を取りうる（例：会議、給食、バス）
  2. 列数が対象の数に比例する（学年6→下校列6〜12列、部活動15→15列／行、学校11→自治体横断表の11列）
  3. 同じ列名でも値の型が違う（学年別「下校時間」列に時刻ではなく時限数が入る学校がある。下校が学年範囲×時刻範囲、記号＋凡例で表される学校がある）
  4. 表の向き自体が違う（月縦表／年間・月横軸／カレンダー格子／週ブロック／2段組み／部活動の転置表）
- したがって固定列スキーマ（date, event, lunch, bus, dismissal …）では原理的に対応できない。

### 1.3 ユーザーから直接得た要件（公開サンプルでは未確認だが必須として扱う）
- バスが無い学校ではバス表自体が不要である。
- 日番・日直は、ある学校／無い学校があり、**夏休みだけある**場合、**1日単位／午前・午後分割**の場合がある。
- 部活動は小学校には無いが中学校にはあり、部活動専用の活動予定表が必要な場合がある。
- 1日の時限は6限／7限／8限など学校で異なる。
- 会議だけの独立列を設けている学校がある（公開サンプルでは会議は埋め込みが主流だったが、独立列も項目定義で当然に作れること）。

### 1.4 非目的（v1でやらないこと）
- 給食の献立そのものの管理（給食の有無・日数集計まで。献立連携は拡張点としてのみ残す）
- 時間割の編成そのもの（school-timetableの責務。ここでは参照・連携のみ）
- 出張・休暇の承認ワークフロー（予定としての記録まで。承認は将来拡張）

## 2. 設計原則

1. **核は最小限に固定し、それ以外はすべて定義にする。**
   固定するのは「学校・年度・日・行事の共通骨格」だけ。列・項目・対象・記号・当番・ビュー・公開範囲は学校がデータとして定義する。
2. **データと表示を分離する。** 同じデータを、月縦表／週表／年間横並び／カレンダー／転置表／生徒用要約として描き分けるのはビューの責務であり、データをコピーしない。
3. **公開範囲はフィルタで表現する。** 職員用／保護者用／生徒用／公開用を別表・別データで持たない。同一データに項目単位・行事単位の公開範囲を持たせ、ビュー側で出し分ける（転記ミスと二重管理を防ぐ）。
4. **値は型付きで持つ。** 時刻・時刻範囲・記号・コード・人名・数値・○×・自由文を区別する。型があるからこそ給食日数・授業日数の集計、検索、バリデーションができる。自由文に何でも埋める設計は採らない。
5. **調査で埋まらなかったケースを設定で吸収する。** 全ケースの事前調査は不可能という前提に立つ。新種の列・当番形態・記号体系が現れても、項目定義・対象軸・当番定義の追加で対応でき、スキーマ変更を要しないことを合格条件とする。
6. **school-timetableとマスタを二重に持たない。** 学校・年度・学年／クラス・教職員・時限／日課は共有マスタとし、行事予定側はIDで参照する（§10。ただし単独利用時は自前マスタで完結する）。

## 3. 全体モデル（概念図）

```
School（学校テナント）
 ├─ SchoolYear（年度）─ Term（学期／期）─ Holiday（祝日・休業日）
 ├─ DayRecord（日ごとの骨格：日課コード, 授業日フラグ, 備考）
 ├─ PeriodPattern（日課パターン：A/B日課, 普/特, 時限定義への参照）
 ├─ TargetGroup（対象軸：学年, 学部, 部, クラス, バス便, 学校…）─ Target（対象の実体）
 ├─ ItemDefinition（項目定義＝「列」の定義）─ ItemOption / Legend（選択肢・記号凡例）
 ├─ DutyDefinition（当番定義：日番, 日直, 週番…）─ DutyAssignment（割当）／ RotationRule（輪番規則）
 ├─ Event（行事：共通骨格のみ）─ EventTarget（対象）─ EventValue（項目別・型付きの値）
 ├─ DailyValue（行事に属さない日次値：給食○×, 清掃, バス便時刻など）
 ├─ ViewDefinition（ビュー定義）─ ViewColumn（列構成）／ ViewFilter（公開・対象フィルタ）
 └─ Publication（公開版・改訂履歴）
```

ポイントは2つある。
- **Event は「行事欄に書かれる出来事」専用にしない。** 出張・〆切・会議・休暇も、共通骨格（件名・日時・対象・公開範囲・確定度）を持つ Event として同じテーブルに載せ、種別は ItemDefinition／Category で区別する。本校シートで 行事データ／出張データ／〆切データ／年休データ がほぼ同型だったことが、この統合の根拠である。
- **「日×項目×対象」の値（DailyValue）が、表のセルの正体である。** 月表の1セルは、(date, item_definition, target) で引ける値の集合として再構成できる。列が12列に増えても、行（部）が増えて転置しても、データ側は増えない。

## 4. テーブル設計（中核）

表記: `PK` 主キー、`FK` 外部キー。すべての業務テーブルに `school_id` を持ち、マルチテナント分離を担保する（school-timetableと同方針）。

### 4.1 学校・年度・暦

| テーブル | 主要カラム | 説明 |
|---|---|---|
| `schools` | id PK, name, school_type（小/中/高/義務教育/小中一貫/特別支援/その他）, prefecture, settings_json | テナント。連携モードでは school-timetable と同一ID体系にする（§10） |
| `school_years` | id PK, school_id FK, year（例 2026）, starts_on, ends_on, term_system（3学期制/2期制/その他）, is_current | 年度。本校「設定」の年度に対応 |
| `terms` | id PK, school_year_id FK, name（1学期/前期/後期課程の期など）, starts_on, ends_on, sort | 学期・期。前期課程／後期課程は「学年の区分」であり学期と混同しないよう、課程は TargetGroup 側で扱う（§4.3） |
| `holidays` | id PK, school_id FK, date, name, kind（祝日/振替/学校休業日/閉庁日） | 祝日・休業日。土日祝の色分けと授業日判定の材料。本校「設定」の祝日リストに対応 |
| `day_records` | id PK, school_id FK, date, day_type（授業日/休業日/行事日/登校日など）, period_pattern_id FK nullable, note | 1日1行の骨格。曜日は date から導出する（保存しない）。長期休業も行を省略せず「夏季休業」等の day_type で継続表現する |

### 4.2 時限・日課

| テーブル | 主要カラム | 説明 |
|---|---|---|
| `period_patterns` | id PK, school_id FK, code（A, B, 普, 特, A7, B6…）, name, description | 日課パターン。「普3日課」「特4日課」「A日課／B日課」はここ。本校の年間カレンダーの日課コード、高校の日課コード埋め込みに対応 |
| `period_definitions` | id PK, period_pattern_id FK, period_no（0=朝, 1..N, 99=放課後 等）, label, starts_at, ends_at | パターンごとの時限構成。**時限数は行数で表現する**ため、5限でも8限でもスキーマは変わらない。朝・放課後・部活動の帯も period_no の番外として同列に扱える（宮崎中の「朝・学・活」3帯分割に対応） |

### 4.3 対象軸（Target）— 列数が増える問題の受け皿

| テーブル | 主要カラム | 説明 |
|---|---|---|
| `target_groups` | id PK, school_id FK, key（grade/club/division/bus_route/class/school…）, name, sort | 対象の軸。学校が必要な軸だけを作る。例：学年、学部・部門、前期課程／後期課程、部活動、クラス、通学班、バス便・コース、学校（自治体横断用） |
| `targets` | id PK, target_group_id FK, code, name, sort, parent_target_id nullable | 軸の中の実体。例：学年軸なら 1年〜6年（または1〜9年、7〜9年表記も name で吸収）、部軸なら各部、バス軸なら ①〜④便／コース名 |

「学年別下校時刻6列」「部別15列」は、列の追加ではなく targets の追加で表現する。これが固定列を破綻させた②（列数の対象比例）への回答である。

### 4.4 項目定義（ItemDefinition）— 「列」の定義

| テーブル | 主要カラム | 説明 |
|---|---|---|
| `item_definitions` | id PK, school_id FK, key（lunch/bus/dismissal/meeting/deadline…）, name（表示名は学校が自由に付ける）, **value_type**, target_group_id FK nullable（この項目がどの軸で分かれるか。null=全校一律）, granularity（日/午前・午後/時限/週/月）, default_visibility（職員のみ/保護者可/生徒可/公開）, is_aggregatable, sort, is_active | 列そのものの定義。バスが無い学校はこの行を作らないだけ。会議列が欲しい学校は value_type=自由文 or 予定リスト で1行作るだけ |
| `item_options` | id PK, item_definition_id FK, code, label, meaning（凡例の説明）, color_hint, counts_as_json（集計条件：例 給食日数に数えるか） | 記号・コードの凡例。○×、●☆△、弁（弁当の日）、A/B日課コード、部活の 練/休/大/前/後/ミ、給食の 通常/先/ー などをここで定義する。凡例がデータになるため、特別支援学校型の記号表記も再現できる |

**value_type の列挙（v1）**
`text`（自由文）/ `event_list`（箇条書きの出来事リスト）/ `time`（時刻）/ `time_range`（時刻範囲：下校 14:30〜14:40 等）/ `symbol`（item_options から選択）/ `code`（日課コード等の短コード）/ `person`（教職員参照）/ `persons`（複数人）/ `number`（時限数・日数等）/ `boolean`（○×）/ `target_time_map`（対象ごとに異なる時刻。ただし通常は target との組み合わせ＋ `time` で表現し、専用型は予備）

**適用例（本校→定義への写像）**
- 給食 → value_type=symbol（○/×）, target=null, is_aggregatable=true（○の日を給食日数として集計）
- スクールバス → value_type=text/time, target_group=バス便（①〜④）。本校の「①②③④ 13:00」は (target=便集合, value) として分解して持つ
- 職員動静 → Event の種別として表現（§4.5）。独立列として見せるかどうかはビュー定義で決める
- 各種〆切 → Event 種別=deadline。提出先は Event の追加項目（item としても定義可）
- 清掃・部活・放課後 → symbol（○/×）の DailyValue

| カラム | 型・説明 |
|---|---|

| category_item_id FK nullable | 種別（行事/出張/〆切/会議/休暇/研修…）。種別自体も ItemDefinition 的に学校が追加できるよう、固定enumにしない |
| title | 件名 |
| **date_precision** | `day`（日確定）/ `range`（期間）/ `month`（月のみ確定）/ `undecided`（時期未定）。未定データ・備考欄の「日付なし行事」・月のみ確定への対応 |
| starts_on, ends_on | 日付。date_precision=month のときは年月のみ意味を持つ |
| starts_at, ends_at, is_all_day | 時刻。終日フラグ |
| period_from, period_to nullable | 時限で表す場合の範囲（時限列を持つ学校・時間割連携用） |
| location_id FK nullable, location_text nullable, description | 場所・説明（本校 行事データの 場所/説明 に対応）。場所は登録済みマスタ（§4.5.1）への参照を正とし、マスタに無い場所は自由入力テキストで保持しつつマスタ候補にできる |
| **certainty** | `confirmed`（確定）/ `planned`（予定）/ `tentative`（仮）/ `draft`（案）。表題の「（案）」、名称内の「（仮）（未定）？」を文字列から分離して属性化する |
| visibility | `staff_only` / `guardian` / `student` / `public`（この行事をどこまで見せるか。項目側の default_visibility と AND で効く） |
| submit_to nullable | 〆切の提出先など、種別固有の代表項目 |
| owner_person_id FK nullable | 主担当（互換・代表表示用）。実際の担当者は複数ありうるため正は `event_assignees`（§4.5.1）とする |
| revision | 版番号。改訂履歴は `publications`／変更ログで保持（§4.8） |
| custom_json | 定義に収まらない学校固有の付随情報の避難先。ただし検索・集計したい値は必ず ItemDefinition＋EventValue に昇格させる運用ルールとする |

| 付随テーブル | 説明 |
|---|---|
| `event_targets` | event_id × target_id。対象学年・対象学部・対象部などを多対多で付ける。「1〜4年」範囲は対象を複数付けることで表現し、文字列で持たない |
| `event_values` | event_id × item_definition_id × target_id nullable → 型付き値（value_text / value_time / value_number / value_option_id / value_person_id を value_type に応じて1つ使用）。Event 固有の追加項目（提出先、出張先の詳細等）をここに逃がす |
| `event_assignees` | event_id × （person_id FK nullable ／ free_text_name nullable のどちらか）× role（担当/出張者/取得者/引率 等）。**複数選択可**。登録済みの人は person_id で参照し、登録の無い外部の人・未登録の表記は free_text_name で保持する。どちらで入れたかを区別し、後から同一人物マスタへ寄せる操作を用意する（判断②の担当者入力に対応） |

### 4.5.1 場所マスタ
| テーブル | 主要カラム | 説明 |
|---|---|---|
| `locations` | id PK, school_id FK, name, kind（教室/体育館/校外/オンライン 等、任意）, sort, is_active | 登録済みの場所。入力時はリストから選択でき、リストに無い場所は直接入力すると location_text として保存され、管理者がマスタへ昇格できる。校外の施設など学校外の場所も同じマスタで扱う（学校に閉じない） |

### 4.6 日次値（DailyValue）— 行事でない「その日の状態」

| カラム | 説明 |
|---|---|
| id PK, school_id FK, date, item_definition_id FK, target_id FK nullable, slot（`all_day`/`am`/`pm`/period_no） , 型付き値カラム群（EventValue と同形式） | 給食○×、清掃、部活の有無、下校時刻（学年別）、バス便時刻、日直以外の日ごとの記入欄はすべてここ。「1日が朝・学・活の3行」も slot で表現できる |

行事予定表の月表は、実際には `Event（その日に重なるもの）＋ DailyValue（その日の項目値）＋ DutyAssignment（その日の当番）` を日ごとに束ねた描画である、と定義する。本校の「結合データ」シートが担っていた役割は、この束ね（クエリ／ビュー）に置き換わる。結合結果を実テーブルに二重保持はしない。

### 4.7 当番（Duty）— 日番・日直・週番の汎用化

| テーブル | 主要カラム | 説明 |
|---|---|---|
| `duty_definitions` | id PK, school_id FK, name（日番/日直/週番/清掃当番/給食当番…学校の呼称をそのまま）, **granularity**（`day`/`am_pm`/`week`/`period`）, **applicable_period**（`all_year`/`term`/`long_vacation_only`/`custom_range` ＋ 開始・終了日）, target_group_id nullable（児童生徒の当番か、教職員の当番か等）, sort | 当番の「種類」の定義。夏休みだけ日直がある学校は applicable_period=long_vacation_only で1定義作る。午前／午後分割は granularity=am_pm |
| `rotation_rules` | id PK, duty_definition_id FK, rule_json（順番リストへの参照、交代曜日、週番の金曜交代 等）, member_target_ids / person_ids | 輪番の自動割当規則。本校「日番リスト（番号・氏名）」に対応。自動生成は下書き作りであり、手動上書き・交代（§4.7.1）を常に優先する |
| `duty_assignments` | id PK, duty_definition_id FK, date（週単位の場合は週開始日）, slot（all_day/am/pm/week）, person_id / target_id nullable, note, is_manual_override, origin（`auto` 自動生成 / `manual` 手入力 / `swap` 交代による） | 実際の割当。日単位・午前午後・週単位を slot と granularity の組合せで同テーブルに載せる |
| `duty_changes` | id PK, school_id FK, duty_definition_id FK, **kind**（`swap` 交換：2つの割当の担当を入れ替える / `substitute` 代行：その回だけ別の人が担い、元担当はその回を免れる / `reassign` 指名し直し）, assignment_a_id FK, assignment_b_id FK nullable（swap の相手。substitute では null で to_person を持つ）, from_person_id, to_person_id, reason（出張・休暇・行事対応 等、自由記述＋種別）, requested_by, status（`proposed` 提案中 / `applied` 適用済 / `declined` 見送り）, created_at, applied_at | **交代の履歴**。交代は割当の上書きではなく、このテーブルに記録される正式な操作として扱う。元の割当がどう変わったかを後から追えること、交代回数の偏りを後で見られることが目的。適用時に duty_assignments 側が更新され、origin=swap になる |

### 4.7.1 交代（swap / substitute）— 頻発する運用を正式機能にする（2026-11-05、荒木の指摘で追加）
当番の交代は例外ではなく日常的に発生する。したがって交代は「セルを書き換える手動修正」で済ませず、次の操作として一級で用意する。
- **交換（swap）**：Aさんの○日とBさんの△日の担当を入れ替える。2つの割当を同時に更新し、片方だけ変わる中途半端な状態を作らない（トランザクションで扱う）。
- **代行（substitute）**：その回だけ別の人が担う。元担当の後日の割当は動かさない。
- どちらの場合も、理由（出張・休暇など）と操作者が duty_changes に残る。表の表示では交代済みであることが分かる印を付ける（元の担当が誰だったかは履歴で確認できる。表自体を履歴で汚さない）。
- 交代の相手は、§4.7.2 の競合検出が提示する候補（その日に予定が無く、輪番上も近い人）から選べる。もちろん候補外の人を直接指定することもできる。

### 4.7.2 競合検出と交代の促進（conflict detection）
当番と本人の予定が重なったときに、**システム側から交代を促す**仕組みを必須とする（2026-11-05、荒木の要件）。

- **検出対象（v1）**
  1. 当番割当の担当者が、その日（slot が午前／午後ならその時間帯）に **出張・休暇・研修** など不在になる予定（Event の assignee／owner として登録されているもの）と重なっている
  2. 同じ人が同じ slot に2つ以上の当番が重なっている
  3. 当番の適用日なのに担当者が未割当（空き）になっている
  検出対象の予定種別は学校が設定できる（出張だけを対象にするか、休暇も含めるか等）。時間の重なりは slot と予定の時間帯（終日／午前／午後／時刻）で判定し、午前だけの出張で午後の日番とは競合にしない。
- **検出のタイミング**：当番の割当・自動生成・交代の適用時と、予定（出張等）の登録・変更時の**両方向**で即時に再判定する。後から出張が入った場合でも競合が立つことが重要である。
- **促し方（ブロックはしない）**
  - 該当セルの当番表示に警告印を付け、未解消の競合一覧（管理者・本人向け）にも載せる
  - 本人と当番管理者に通知し、「交代を手配する」導線を出す。導線の先では候補（その日に不在予定が無く、輪番順が近い人）を提示し、交換／代行をその場で適用できる
  - 競合は**警告であって禁止ではない**：短時間の出張で日番と両立できる場合などもあるため、理由を付けて「このままにする（解消済みとして扱う）」ことも選べる。その判断も記録に残す
- **データの置き場**：競合は保存する実体ではなく、割当と予定から**導出する判定結果**として扱う（解消状態・見送り理由だけを `duty_conflict_waivers`（assignment_id × event_id × waived_by × reason）に記録する）。予定側が消えれば競合も自然に消える。

### 4.8.1 標準レイアウトカタログ（2026-11-05、荒木の指定で確定）
学校が選べる表示スタイルとして、次の5種を標準レイアウトとして実装する。いずれも同じデータ（Event／DailyValue／DutyAssignment）への描画であり、レイアウトを切り替えてもデータは変わらない。列に何を出すかは全レイアウト共通で view_columns が決める（ただし L3・L4 は幅の制約上、出す項目を絞る前提で列構成を持てる）。

| # | layout キー | スタイル | 構造 |
|---|---|---|---|
| L1 | `month_rows` | **1ヶ月を縦に見る** | 1日1行 × その月の全日。列＝view_columns（行事・動静・〆切・日番・バス・給食…）。本校「行事予定表」と同型で、職員用月表の主形式 |
| L2 | `week_rows` | **1週間／2週間を縦に見る** | 1日1行 × 7日または14日（layout_params で選択）。列構成は L1 と同じ。週の開始曜日は学校設定に従う。本校「週予定表」と同型 |
| L3 | `year_columns` | **縦表を横につないだ1年分** | L1/L2 と同じ「1日1行の縦表」を月ブロックとして、4月→3月を**右方向に12ブロック並べる**。行は日（1〜31）で全月そろえ、存在しない日（2月30日など）は空セルにする。各月ブロックの列は、年間俯瞰用に絞った列構成（例：日・曜・行事のみ、または行事＋給食）を持てる。横スクロール前提の画面表示と、A3／横長の印刷を想定する |
| L4 | `calendar_grid` | **曜日で折り返す月カレンダー** | Googleカレンダー月表示と同型：週を行、曜日（7列）を列とし、各日のマスに予定を並べる。マス内は表示件数に上限を設け、超過分は「他○件」とし、クリックでその日の詳細（L2 の1日分相当）を開く。複数日にまたがる予定は期間バーとしてつないで表示できる |
| L5 | `week_timeline` | **1日のタイムラインを1週間分横に並べる** | 列＝週の各日（7列）、縦軸＝時刻。時間を持つ予定を開始〜終了時刻の位置・長さで配置する（Googleカレンダーの週表示と同型）。縦軸の範囲と目盛りは layout_params（例：7:00〜19:00、30分／1時間刻み）で設定でき、**時限軸モード**（縦軸を時刻ではなく時限 1〜N限＋朝・放課後にする）も選べる。終日予定と時刻のない予定は各列上部の「終日帯」に並べる。時間が重なる予定は横にずらして並置する |

**レイアウトごとの入力・印刷の扱い**
- セル直接入力（§6）は L1・L2・L3 でそのまま使える（セル＝日×列が一対一に対応するため）。L3 は列構成が絞られるため、入力できるのは表示中の列に対してのみとする。
- L4 では、マスへの直接タイピングではなく「日マスを選んで入力開始」とし、確定後のオブジェクト化と詳細モーダル（§6.2〜§6.3）は他レイアウトと同一にする。予定オブジェクトのクリックでモーダルが開く点も共通。
- L5 では、タイムライン上の時間帯を選んで入力を始めると、その時間が予定の開始〜終了の初期値として詳細モーダルに渡る。時刻のない予定は終日帯で L1 と同様に入力できる。
- 印刷／PDF（§9.1）の主対象は L1・L2・L3（表形式）とし、L4 は A4 1枚の月カレンダーとして印刷可能にする。L5 は画面表示を主とし、印刷は対象外（必要になれば Phase 3 以降で検討）とする。
- 拡張レイアウトとして、部活動の転置表（`transposed`）と生徒用の2段組みは本カタログの5種とは別に保持する（§4.8、§5.1）。

### 4.8.2 対象別セルの同値グループ化表示（2026-11-05、荒木の提案で追加）
対象軸で分かれる項目（学年別下校時刻、学年別バス、学部別下校など）のセル表示では、**値が同じ対象同士をまとめて表示する**ことを標準とする。これはデータの持ち方ではなく描画の規則であり、データは常に対象ごとに保持する（daily_values は対象別が正）。

- **規則**
  - 全対象の値が同じ → 対象範囲をまとめて1回だけ表示する。例：`1～6年 14:30～14:40`
  - 一部の対象だけ同じ → 連続する対象のまとまりごとに表示する。例：`1～4年 14:30～14:40／5・6年 15:20～15:30`（調査で確認した加古川・平岡小の実表記と同型）
  - 連続していない対象が同じ値（例：1・3年だけ同じ）→ 範囲（～）にせず列挙する。例：`1・3年 14:30`
  - 全対象が異なる → 全てを個別に表示する。例：学年ごとに1行ずつ時刻を並べる
  - 対象の範囲・列挙のラベルは、対象の並び順（sort）と短い表示名から生成する。数値でない対象（学部名・部門名など）では範囲表記は使わず列挙のみとする
- **対象は下校時刻に限らない**：対象軸を持つ項目すべて（バス便の時刻、給食の有無、時限数など）に同じ規則を適用できる。view_columns.group_same_values で列ごとに有効／無効を切り替えられ、既定は有効とする。学年別に列を分けた表示（千郷小型の12列形式）を使うビューでは無効にする。
- **編集との関係**：グループ表示された塊をクリックすると、その塊に属する対象の値が編集対象になる。1つの対象だけ値を変えれば、表示上は自動的にグループが分かれる（例：3年だけ変更 → `1・2・4～6年 …` ではなく、連続性に基づき `1・2年／3年／4～6年` の3塊になる）。逆に、複数対象を選んで同じ値を入れれば再びまとまる。「全学年に同じ値を入れる」一括入力も編集側の操作として用意する。
- **印刷**：この規則は画面・印刷（§9.1）の両方に同じに適用する。紙の行事予定表で一般的な省略表記そのものであるため、印刷時の可読性が上がる。

### 5.2 設定シナリオ（受け入れテストとして使う）
次の各ケースが、コード変更・スキーマ変更なしに設定だけで再現できることを、設計の合格条件とする。

1. バスの無い学校：項目定義にバスが存在しない。ビューにも現れない。
2. バスがあり学年別に下校・バスが分かれる学校：対象軸=学年、項目=下校（time）＋バス（time/方式text）で12列ビューを構成できる。
3. 日直が無い学校／日単位で人名が入る学校／週番と併記する学校：当番定義 0件／1件（day）／2件（day＋week）で表現できる。
4. 夏休みだけ日直があり、午前・午後で人が替わる学校：当番定義1件、applicable_period=long_vacation_only、granularity=am_pm で表現できる。
5. 部活動：小学校では定義なし。中学校では「全校一律の記号（ノー部活デー等）」としても、「部ごとの別表（部が列／部が行の転置）」としても表現できる。
6. 時限：6限校／7限校／8限相当校（日課コードで入替）が period_patterns／period_definitions の行数とコードで表現できる。時限ごとの教科列が必要な学校は、ビュー列に時限を指定できる。
7. 会議の独立列がある学校：項目定義に会議（event_list）を1件追加し、ビューに列として置ける。逆に会議を行事に埋め込む学校は列に置かないだけでよい。
8. 職員動静（出張・〆切・休暇）を職員用にだけ出す学校：Event の visibility と項目の default_visibility で、生徒・保護者ビューから自動的に落ちる。
9. 未定行事：日が決まっていない行事を date_precision=month／undecided で登録でき、月表の末尾「○月の未定イベント」欄（本校方式）と年間表の備考欄の両方にビューで出せる。
10. 学期制：3学期制／2期制（前期・後期）／義務教育学校の前期課程・後期課程を、terms と target_groups の使い分けで混同なく表現できる。

- ビューの編集（列の追加・削除・並び替え、対象者、レイアウト選択、プレビュー）

- プリセットの適用と、他校テンプレートの取り込み（将来）

## 6. 入力UX設計（判断②確定：セル直接入力＋オブジェクト化）

### 6.1 基本方針
入力の主経路は、**行事予定表のセルへの直接の文字入力**とする。別画面のフォームを正とはしない（v0.1 §10 の案を判断②で置き換えた）。
セルに入力された文字列は保存時点でそのままテキストとして残るのではなく、**予定オブジェクト（Event）として生成**される。セル内に表示される各予定はオブジェクトであり、クリック／タップで詳細編集モーダルが開く。

### 6.2 セル編集の流れ（状態遷移）
1. セルを選択し、そのままタイプするとテキスト入力が始まる（スプレッドシートと同じ感覚にする。二重クリックを必須にしない）。
2. **Enter** でその文字列が1件の予定オブジェクトとして確定する。同時に、入力した予定の**真横にクイック入力ポップオーバー**（§6.5）が開き、担当者→場所→時間の順に、リストから選ぶだけで詳細を続けて付けられる。全画面の詳細モーダルへいきなり遷移させない（入力の流れと視線をセルから離さないため）。
3. 詳細はすべて任意である。ポップオーバーを途中で閉じる（Esc／外側クリック）操作をした時点で「その時点まで入力した内容＋件名のみの予定」として保存済みの状態であり、詳細を入れなかったことで入力が消えることはない。各ステップには「スキップ」があり、必要な項目だけ付けて終われる。
4. セル内に次の予定を続けて入力できる。1セル＝複数オブジェクト（箇条書き表示）であり、オブジェクトごとに独立して編集・削除できる。
4.1 **ドラッグ＆ドロップで別日へ移動できる**（2026-11-06、荒木の指示で試作に含める。当初は Phase 2 候補だったもの）。予定オブジェクトを掴んで別の日のセルへ落とすと、その予定の日付が移動先の日に変わる（時刻・担当者などの詳細は保持する）。複数日にまたがる予定は期間ごと移動する。移動は通常の編集と同じく保存され、対象レイアウトは行表（L1／L2）とカレンダー格子（L4）を基本とし、年間表（L3）・週タイムライン（L5）でも同じ操作で日を移せることが望ましい。誤ドロップ対策として、ドロップ先セルのハイライト表示と、移動直後に気づける視覚フィードバックを持つこと。
5. 既存オブジェクトのクリックでは**詳細編集モーダル**（§6.3）が開き、詳細の追加・修正ができる（モーダル自体の出来は荒木が確認済みで、そのまま正式の詳細編集画面とする）。件名のテキストもモーダル内およびセル内再編集の両方で直せる。ポップオーバー内にも「詳細を開く」導線を置き、いつでもモーダルへ移れる。
6. 行事でない列（給食○×、下校時刻、当番など DailyValue／Duty の列）では、Enter 確定時の挙動は列の value_type に従う（記号列なら選択、時刻列なら時刻入力 §6.3）。この場合も「入力した値が型付きの値オブジェクトになる」原則は同じである。

### 6.3 詳細入力モーダルの構成
モーダルは、よく使う項目を上位に置いた段階的開示とする。項目の顔ぶれは学校の項目定義・行事種別に応じて変わる（学校に無い項目は出ない）。

| 項目 | 入力部品の仕様 |
|---|---|
| 件名 | テキスト（セルで入力した文字列が初期値） |
| 時間 | **アナログ時計盤ピッカー**（Android 等で一般的な、時→分の順に盤面で選ぶタイプ）を標準とする。開始・終了の両方に用意し、直接の文字入力（例 `13:30` のタイプ）も常に可能とする。終日の切替あり。時限で指定したい学校向けに、時計盤と並んで「時限で指定」（period_definitions から選択）も選べるようにする。5分刻みを既定とし、盤面はタップ／クリック両対応にする（GIGA端末のタッチ操作を想定） |
| 場所 | **コンボボックス（選択＋直接入力の両対応）**。登録済みの場所（locations）があればリスト表示され、そこから選べる。リストに無い場所はそのまま文字入力でき、保存時に location_text として保持され、マスタへの追加候補になる |
| 担当者 | **複数選択コンボボックス（選択＋直接入力の両対応）**。あらかじめ登録されている人（教職員マスタ＋学校が登録した外部関係者）がリスト表示され、複数選択できる。リストに無い人は直接入力でき、free_text として保持される（§4.5 event_assignees） |
| 対象 | 対象軸（学年・部・クラス等）からの複数選択。セルの列・行から推定できる場合は初期値を入れる |
| 種別・公開範囲・確定度 | 種別（行事/会議/〆切 等）、公開範囲（職員のみ/保護者/生徒/公開）、確定度（確定/予定/仮）。既定値は列（ビュー列）の定義から引き継ぎ、通常は触らなくてよい位置に置く |
| メモ・提出先など | 種別固有の項目（〆切の提出先など）。テキスト |

### 6.3.1 モーダルとカードは「種別ごとの構成」にする（2026-11-06、荒木の指摘）
詳細モーダル（§6.3）とクイック入力カード（§6.5）は、全種別共通の1画面にしない。**種別ごとに、出す項目・項目のラベル・セルでの表示の仕方を変える**（種別テンプレート）。共通画面のままだと、休暇のように「主役が件名ではなく人」である種別で、ラベルも表示も実態に合わなくなるためである。

- **人のラベルは種別で変える**：行事＝担当者、〆切＝担当者、出張＝出張者、**休暇＝休暇取得者（取得者）**。event_assignees の役割（role）として種別テンプレートが決める。
- **セル表示の主役も種別で変える**（display_source）：
  - 行事・会議・〆切など：件名が主役（現行どおり）。
  - **休暇：取得者名が主役**。表示は「取得者名（分類）」の形（例：`荒木（年休）`）とし、取得者が複数のときは並べて表示する。件名は表示の主役にしない。
  - 出張：出張者名＋件名（用務）の併記を既定とする。
- **休暇の入力とモーダルの扱い**：
  - 休暇列のセルに打った文字列は、件名ではなく**取得者名**として扱う（クイック入力カードのステップ1も「取得者」ラベルになる）。件名は「取得者名＋分類」から自動生成して内部に保持し、休暇用モーダルに件名欄は出さない（必要な補足はメモ欄で受ける）。
  - 休暇用モーダルの項目は 取得者／休暇分類／時間帯（終日・午前・午後・時間指定）／メモ とし、場所・対象などの無関係な項目は出さない。
- **一般化**：種別テンプレート（項目構成・ラベル・表示主役）は学校が定義・変更できること。初期テンプレートは 行事／出張／〆切／休暇 の4種を用意し、新しい種別を作るときは最も近いテンプレートを複製して調整できる形にする。これは §6.5 の「ステップは種別ごとに変える」と対になる、モーダル側の規則である。

### 6.4 入力部品の共通原則
- **「リストから選ぶ」と「直接打つ」は常に両立させる。** 場所・担当者に限らず、選択式の項目はすべて新規文字列の直接入力を許す。登録済みデータが不完全な現場でも入力が止まらないことを優先する（マスタの整備は入力の前提条件にしない）。
- 直接入力された新しい値は、黙ってマスタ化せず「候補」として保持し、管理者が後からマスタへ昇格・既存への統合ができる。
- キーボード操作を完結させる：Enter=確定して詳細へ、Esc=詳細を閉じて件名のみで保存、という §6.2 の流れを崩さない。マウス／タッチでも同じ結果になること。

### 6.5 クイック入力ポップオーバー（2026-11-05、荒木の提案で追加）
入力直後の詳細付けは、全画面モーダルではなく、**入力した予定の真横に出る小さな段階式ポップオーバー**で行う。モーダルは「既存予定をじっくり編集する画面」、ポップオーバーは「入力の勢いのまま最低限の詳細を付ける画面」と役割を分ける。

- **段階フロー**：ステップは 担当者 → 場所 → 時間 の順（荒木の提示した順序）。1ステップ＝1項目だけを表示し、選択・確定すると次のステップへ自動で進む。ステップ表示（例 ●-○-○）と「戻る」を持ち、途中のステップへ戻って直せる。
  - **担当者**：登録済みの人のリストを提示し、複数選択＋直接入力（§6.4 の原則どおり）。「確定」で次へ。選択なしでも進める（スキップ相当）。
  - **場所**：登録済みの場所リスト＋直接入力。確定で次へ。
  - **時間**：コンパクトなアナログ時計盤（開始→終了）＋直接の文字入力＋終日切替。モーダルと同じ部品を小さくしたもので、挙動は §6.3 と一致させる。
  - 最終ステップの確定でポップオーバーは閉じ、入力は完了する。各ステップの値は**確定のたびに即保存**する（途中で閉じても付けた分は残る）。
- **表示位置**：入力したセル（予定オブジェクト）に隣接して表示し、画面端では自動で反対側・上下に回り込む。表のスクロールに追従し、対象の予定が見えなくなる位置には置かない。
- **中断と再開**：Esc／外側クリックでいつでも閉じられる。その場合も予定オブジェクトと入力済みの詳細は保存済み（§6.2-3）。後から付け直す場合はオブジェクトのクリックでモーダルを開く。
- **キーボード（2026-11-06、荒木の実使用フィードバックで具体化）**：
  - ポップオーバーが開いたら、そのステップの入力欄に**自動でフォーカス**する。クリックを挟まず、そのままキーボードで打ち始められること。ステップが切り替わるたびに、次のステップの入力欄へフォーカスが移る。
  - **Enter＝そのステップを確定して次へ進む**（最終ステップでは確定して閉じる）。リスト内は ↑↓ で移動し、Enter で選択＝確定として扱う。
  - **担当者ステップの例外**：担当者は複数人を続けて入れることが多いため、入力欄での **Ctrl+Enter＝入力中の氏名を担当者として追加し、入力欄を空にして同じステップに留まる**（次の担当者を続けて打てる）。通常の Enter は、入力中の氏名があればそれも追加したうえで、ステップを確定して場所へ進む。「追加」ボタンも従来どおり使える（Ctrl+Enter と同じ動作）。
  - **ステップ見出し（1.担当者／2.場所／3.時間）はクリック可能**とし、クリックでそのステップの入力画面へ直接移動できる（前後のステップを行き来して直せる）。キーボードでもステップ間を移動できる導線を持つ。
  - タッチでも同じ大きさ・同じ順序で操作できる。
- **出す項目は学校の定義に従う**：学校に場所マスタが無い、担当者を付けない運用、などでは該当ステップ自体を出さない。ステップの構成と順序は項目定義・ビュー定義から決まり、コード変更なしに学校ごとに変えられること。
- **ステップは予定の種別ごとに変える（2026-11-06、荒木の指摘で具体化）**：ステップ構成は種別（行事／出張／〆切／休暇 等）ごとに定義できること。代表例は休暇である。
  - **休暇の予定では「場所」ステップを出さない**。休暇に場所は意味を持たないためで、代わりに **「休暇分類」の選択ステップ**を出す。選択肢は学校が定義するコード項目（item_options）で、**リストの内容は設定画面で編集できる**こと。初期値は荒木の指定（2026-11-06）で **年休／病休／特休／夏特／看護／職専免／振休／その他** の8項目とする。
  - 休暇の残りのステップは 担当者（＝取得者）→ 休暇分類 → 時間帯（終日／午前／午後／時間指定＋開始・終了時刻。本校の年休データの「時間帯」と同じ扱い）とする。
  - 同じ考え方を他種別にも広げられること：〆切なら場所の代わりに「提出先」、出張なら場所は残しつつ用務先として扱う、など。種別固有の項目は events の共通骨格ではなく event_values（種別固有項目）として保持する（§4.5 の原則どおり）。
- **モーダルとの関係**：ポップオーバーはモーダルの代替ではなく前段である。ポップオーバー内に「詳細を開く」を置き、対象・公開範囲・メモなどポップオーバーに無い項目はモーダルで扱う。Enter 直後にいきなりモーダルを開く従来動作を好む学校向けに、設定で初期動作（ポップオーバー／モーダル）を切り替えられるようにする（既定はポップオーバー）。

## 8. 集計の扱い
- 授業日数・給食日数（月末・年間、学年別例外値つき）は保存値にしない。day_records.day_type と daily_values の記号（item_options.counts_as_json）から**導出**する。

- 最終下校時刻のような「月単位の1値」は、daily_values の月集計（最大値）として出すか、月のメタ情報として明示登録するかをビューで選べるようにする。

## 9. 権限・公開の原則
- 閲覧は audience（職員／保護者／生徒／公開）と、項目・行事の visibility の AND で決まる。URLを知っていること自体を権限にしない。
- 編集権限は学校内の役割（管理者／行事担当／一般教職員）で分ける。当番・日直の人名など個人情報を含む項目は、公開ビューへの露出を default_visibility=staff_only で既定で防ぐ（公開PDFに日直の人名が載っていた実例があったため、既定は閉じる側に倒す）。
- 生徒・保護者ビューは「見せない項目を隠す」のではなく「見せる項目だけを列に含む」ホワイトリスト方式とする。

### 9.1 PDF／印刷出力（判断④確定：正式出力として持つ）
- **位置づけ**：PDF／印刷はおまけの書き出しではなく、保護者配布・教室掲示・職員室印刷のための**正式な出力経路**とする。アカウントを持たない保護者へ渡す手段でもある。
- **生成元**：PDFは専用の書類データを作らず、**ビュー定義からそのまま生成**する。画面の月表と紙の月表が食い違わないことを原則とする。したがって印刷でだけ出る／出ない情報は、ビューの列構成と visibility で表現し、印刷専用の手直しデータは持たない。
- **印刷設定**：`view_definitions` に print_settings を持たせる：用紙（A4／A3）、向き（横／縦）、余白、文字サイズの段階、ヘッダー（学校名・対象月・版ラベル「○月○日修正」）、フッター（ページ番号）。月表は A4横／A3、生徒用の2段組みのような紙向けレイアウトもビューの layout として選べる。色分け（土曜青・日曜祝日赤）は印刷でも保持する（白黒印刷でも曜日が判別できるよう、色だけに依存しない表記を併用する）。
- **版との紐付け**：生成したPDFは `publications` の版と紐付くスナップショットとして保持し、「どの版のPDFをいつ配ったか」を追えるようにする。データを直したら旧PDFは旧版のものとして残り、新しい版のPDFを生成する（ファイル差し替え運用の曖昧さをここで解消する）。
- **実装段階**：Phase 1 では月表（職員用・保護者用）のPDF／印刷までを正式対応とし、年間表・転置表など他のレイアウトの印刷最適化は Phase 2 で広げる。

## 10. school-timetable との連携設計（判断①確定：独立アプリ＋連携可能）

### 10.0 確定した前提（2026-11-05、荒木の判断）
- **内包しない。独立アプリとする。** 理由は利用パターンが学校によって異なるためである：行事予定だけを使う学校／時間割だけを使う学校／両方使う学校、の3パターンがありうる。
- この利用パターンの違いは、**料金設定をパターンで変える**考えにもつながる。したがって製品境界は課金境界でもある：各アプリが単独で契約・利用開始・解約でき、両方使う場合にだけ連携が有効になる設計にする。
- 含意：行事予定アプリは、school-timetable が無い学校でも**単独で完全に動作しなければならない**。連携は「あると便利」ではなく「両方ある学校でのみ効く追加価値」と位置づける。

### 10.1 利用パターンと契約（entitlement）
| パターン | 行事予定 | 時間割 | 連携 |
|---|---|---|---|
| A | ○ | － | なし（行事予定が自前マスタを持つ） |
| B | － | ○ | なし（本アプリの対象外） |
| C | ○ | ○ | 有効（マスタ参照・日課リンク・SSO） |

- 契約・課金単位を表す `product_entitlements`（school_id × product（event_schedule / timetable）× plan × status × 有効期間）を共通基盤側に持つ想定とする。料金表そのものは本設計の対象外だが、「製品ごとに学校単位で有効／無効を切り替えられる」ことを境界の要件とする。
- 片方の解約・停止が、もう片方のデータと動作に影響しないこと（連携参照が切れても行事予定側は自前マスタへフォールバックできること、§10.2）を要件とする。

### 10.2 マスタの二つのモード（単独／連携）
連携時にマスタを二重管理しない（§2 原則6）ことと、単独でも完結すること（§10.0）は両立させる必要がある。そこでマスタは次の二つのモードを持つ。

| 共有マスタ候補 | 単独モード（パターンA） | 連携モード（パターンC） |
|---|---|---|
| 学校テナント・利用者・教職員 | 本アプリ側で保持（担当者リストの正） | 共通基盤／school-timetable 側を正とし、IDで参照 |
| 年度・学期 | 本アプリ側で保持 | 共通基盤を参照 |
| 学年・クラス構成 | targets（学年軸）として本アプリ側で保持 | school-timetable の構成を参照し、表示名・並びの上書きのみ本アプリ側に持つ |
| 時限・日課パターン | 本アプリ側で保持（時限列が要る学校向け） | school-timetable 側を参照し、複製しない |
| 場所（locations） | 本アプリ側で保持（時間割と共有する必然性は低いため、連携モードでも原則本アプリ側を正とする） | 同左 |

- 各マスタには出所を示す `source`（`local` / `linked` ＋ 連携先ID）を持たせ、モード切替時に「ローカルで持っていたマスタを連携先へ寄せる（名寄せ）」移行操作を用意する。切替でデータを失わないことを要件とする。

### 10.3 連携の境界
- 連携は**共有ID＋API／イベント連携**に限定する。相手の内部テーブルへの直接依存は避ける。
- 行事が時間割に影響するケース（短縮日課、時限入替、考査日課、行事による授業変更）は、Event に `affects_timetable` 相当のリンク（対象日・日課パターンへの変更指定）を持たせ、school-timetable 側がそれを読んで反映する形を将来フェーズで設計する。v1では「日課コードをその日に指定できる（day_records.period_pattern_id）」までを連携の最小形とする。
- 逆方向（時間割側の変更授業・代休が行事表に影響）も、day_type と日課の参照を通じて自然に表示へ反映される。

### 10.3 ID・命名の注意
- 学年の表記（1〜6年／7〜9年／1〜9年）はIDではなく表示名で吸収する。義務教育学校の「前期課程／後期課程」は学年軸とは別の target_group として扱い、学期の「前期／後期」と混同しない。

## 11. 判断事項の状況
### 確定済み
1. **配置形態（2026-11-05 確定）**：内包せず**独立アプリ＋連携可能**とする。理由：行事予定のみ／時間割のみ／両方、の利用パターンがあり、パターンによって料金設定を変える考えもあるため（§10.0）。
2. **入力の主経路（2026-11-05 確定）**：**セルへの直接文字入力を正**とする。入力した文字は予定オブジェクト化し、クリックで詳細編集モーダルが開く。Enter 確定後に時間（アナログ時計盤＋直接入力）・場所（リスト選択＋直接入力）・担当者（リストから複数選択＋直接入力）などの詳細を続けて入力できる作りにする（§6）。
3. **当番の交代と競合検出（2026-11-05 確定）**：自動割当は単純輪番の自動生成＋プレビューを土台とし、それ以上に**交代を正式機能とする**。交代は日常的に発生するため、交換／代行を履歴付きの操作として用意する（§4.7.1）。あわせて、**出張等と日番が重なった場合に交代を促す仕組みを必須**とする：競合を両方向（割当変更時・予定登録時）で検出し、警告と候補提示で交代手配へ誘導する。ブロックはしない（§4.7.2）。

4. **公開の出し方（2026-11-05 確定）**：**PDF／印刷を正式な出力として持つ**（推奨案を採用）。ビュー定義から生成し、公開の版と紐付けたスナップショットとして保持する（§9.1）。Phase 1 は月表のPDF／印刷まで、他レイアウトの印刷最適化は Phase 2。
5. **表示スタイル（2026-11-05 確定）**：標準レイアウトは5種とする — L1 1ヶ月の縦表、L2 1週間／2週間の縦表、L3 縦表を右につないだ1年分（4月〜3月）、L4 曜日で折り返す月カレンダー（Googleカレンダー型）、L5 1日のタイムラインを1週間分横に並べた表示（§4.8.1）。

### 残る参考情報（判断事項ではない）
5. **日直の午前／午後・長期休業のみ等の実例の詳細**：公開サンプルで確認できなかった形態であり、実例を知る荒木からの補足があると当番定義の粒度設計を確定できる。ただし設計自体は粒度（day/am_pm/week）と適用期間（長期休業のみ等）をパラメータとして既に吸収済みであり、補足がなくても実装は進められる。
