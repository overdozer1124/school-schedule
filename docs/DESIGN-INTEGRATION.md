## 0. 確定した判断

| # | 論点 | 決定 |
|---|---|---|
| 連携1 | 画面と行事の入力 | 時間割アプリにある「行事予定」ボタンは削除する。代わりに、両方を契約している学校だけに**行事予定⇔時間割の切り替えスイッチ**を出す（片方だけの契約では出さない）。両方契約の学校では、互いのデータの参照と**逆編集**（相手側の画面からの編集）を、挙げた例に限らず一般的にできるようにする |
| 連携2 | 双方向の仕組み | データごとに**持ち主を1つ**決め、保存は必ず持ち主が行う。相手の画面からの編集は持ち主の API を呼ぶ。変更はイベントで即時に知らせる |
| 連携3 | 持ち主 | 両アプリにかかわるデータは、**契約と無関係に共通基盤**に置く：学校暦（日の種別と日課・行事とその影響範囲・教職員の不在）と共通マスタ（教職員・学年クラス・時限） |
| 連携4 | 時間割のコマへの反映 | 学校暦の変更は**即時に時間割の画面へ表示**し、影響を受けるコマに印を付ける（出張者のコマは代講待ちにする）。コマを消す・動かす変更は**時間割担当が下見して確定**する。時間割を自動では書き換えない |
| 連携5 | 学校暦を編集できる人 | 行事予定か時間割の**どちらかで Editor 以上**なら編集できる。不在は本人が「仮」で登録し、どちらかの Editor が確定する（D-6）。誰がどのアプリから変えたかを記録する |
| 連携6 | 既存データ | 学校暦ができたら、時間割の既存データ（年間行事など）を**学校ごとに一括で移す**。学校ごとに切り替え、戻せるようにする |
| 連携7 | 片方を解約したとき | 学校暦と共通マスタは**そのまま残り**、残った製品から使える。解約した製品の固有データは閲覧・書き出しだけできる状態で**一定期間保管**し、再契約すれば元に戻る。期間を過ぎたら削除する。切り替えスイッチは消える |

連携3 を決め直した理由（荒木の回答、原文）：

> なぜこれの見直しが必要かというと、最初は行事予定だけとか時間割だけ契約していたけど、あとから追加で両方の契約にした場合、それまで片方だけにしかデータ項目が存在しなかった場合、あとからの追加で不具合が生じるのではないかと考えたからです。例えば行事予定で月曜日を水曜授業にするという予定を入力したとして、これは単純に予定としてだけ登録されており、その後に時間割を契約したとしても時間割が変更されるわけではないと思います。しかし最初から時間割にもデータとして反映できるような構成にしておけば後からの連携もしやすいのではないかと考えたのです

連携1 の回答（原文）：

> 行事予定側が正本で良いが、時間割アプリにある行事予定ボタンは削除する。その代わりに、行事予定と時間割の切り替えスイッチを付けて画面を切り替えられるようにする。片方しか契約していない場合はこのスイッチを表示しないか、切り替えができないようにする
> なお、両方契約している場合は、双方のアプリから必要なデータへの参照を許可する。例えば時間割側で年間の時間割を設定する際に、ある日の時間割を曜日変更を行った場合、それを自動的に行事予定に水曜授業などという形で曜日変更があることを行事予定に表示できたり、行事予定で1～4限は音楽祭などと設定した場合、時間割側に行事として追加されるといった形が可能にする。また、それぞれは逆編集も可能にする。これは一例であり、その他様々なケースが考えられるので、ここで挙げた一例だけを実装予定とするのではなく、様々なケースを考えて対応可能にしてください。

連携1 の「行事予定側が正本」は、連携3 の見直しで「行事は共通基盤の学校暦が正本で、行事予定アプリはその主な入力画面」に置き換わった。

## 1. 全体像

```
school-manage.jp
 共通基盤 ─────────────────────────────────────────────
  ├ 学校・利用者・ログイン・役割・契約・年度・学期（DESIGN-AUTH-TENANCY）
  ├ 共通マスタ：教職員／学年・クラス／時限（日課パターンと時限の時刻）
  └ 学校暦：日の種別と日課／行事と影響範囲／教職員の不在   ← 契約と無関係にここが正本
        │  変更イベント（school_id 付き）
   ┌────┴─────────────┐
 行事予定アプリ             時間割アプリ
  固有：日次項目（給食・下校…）、   固有：コマ・版・代講・時数、
  当番、ビュー・印刷・発行、       配置禁止、自動配置、指導計画
  集計
```

- 片方だけを契約した学校でも、学校暦と共通マスタは共通基盤にある。行事予定だけの学校で入れた「月曜を水曜授業」は、**最初から時間割に効く形（型付きの日課データ）で**学校暦に入る。あとから時間割を契約すれば、移行なしにそのまま効く。
- 各アプリの DB には、そのアプリにしか意味のないデータだけが残る。

### 1.1 DESIGN.md §10.2（マスタの二つのモード）への影響

§10.2 の「単独モードではアプリが自前マスタを持ち、連携モードでは相手を参照する」は、この決定で**不要になる**。マスタは最初から共通基盤にあるので、モードの切り替えも名寄せの移行もない。
試作の `master_links`・`link_mode`・`*_source` は役目を終える。本実装では作らず、§10.2 は「共通基盤の共通マスタを参照する」に改める。

## 2. 学校暦のデータ（型付き）

自由文では時間割に効かせられないので、学校暦は「何が・いつ・どこに効くか」を型で持つ。新しい種類のケースが出てきたら、**種類（kind）を足せば済む**作りにする（連携1「様々なケースに対応可能に」）。

### 2.1 日（day）

| 種類 | 中身 | 例 |
|---|---|---|
| `day_type` | 日の種別 | 授業日・休業日・長期休業・登校日・行事日 |
| `day_schedule` | その日に使う日課 | 短縮日課・考査日課・特別日課（共通マスタの日課パターンを指す） |
| `weekday_swap` | 曜日の読み替え | 「11/9（月）は水曜の時間割で授業」 |

### 2.2 行事（event）と影響範囲

行事は、今の行事予定アプリの予定（件名・種別・日時・場所・担当・公開範囲・確定度）を共通基盤へ移したものである。これに**影響範囲（impacts）**を0個以上付ける。影響範囲が無い行事は「表示だけの予定」になる。

| 影響の種類 | 中身 | 時間割での意味 |
|---|---|---|
| `block_periods` | 何限から何限、どの対象（全校／学年／クラス／特別支援学級／教室） | その時間のコマを止める（例：1〜4限 音楽祭） |
| `replace_periods` | 止めた時間に別の活動を入れる。時数に数えるか（`counts_as`：数える／数えない／自動） | 行事を授業時数に数えるかの判断材料（時間割の `plan_consumption` に対応） |
| `room_use` | 教室・場所の使用 | その教室を使うコマを止める |

### 2.3 教職員の不在（absence）

| 項目 | 中身 |
|---|---|
| 人 | 共通マスタの教職員 ID |
| いつ | 日付（期間）と、終日・午前・午後・何限から何限 |
| 種類 | 出張・研修・休暇・その他（時間割の `lesson_cover_cases.absence_type` に揃える） |
| 休暇の分類 | 管理者と本人にだけ返す（D-5）。時間割には「休暇」としか渡さない |
| 確定度 | 仮／確定（D-6）。時間割の代講待ちは確定したものだけに付ける |

試作では出張・休暇は「予定」の一種として扱ってきた。本実装では、行事予定の画面では引き続き予定として見せ、保存先は不在のデータとする。当番の競合検出は、この不在を読む。

### 2.4 共通マスタ

| マスタ | 中身 | 各アプリに残すもの |
|---|---|---|
| 教職員 | 氏名・略称・表示順・利用者との紐付け | 時間割：担当教科・持ち時数など。行事予定：当番の輪番の顔ぶれ |
| 学年・クラス | 学年・クラス・特別支援学級・学年の区分（前期課程など） | 行事予定の対象軸（targets）のうち学年・クラスは共通マスタを参照する。部活動・バス便などは行事予定に残す |
| 時限 | 日課パターンと各時限の時刻 | 行事予定の時限の選択、時間割の時間枠 |

## 3. 編集と変更の伝え方

### 3.1 編集（連携2・連携5）

- 学校暦と共通マスタへの書き込みは、すべて共通基盤の API を通す。どちらのアプリの画面から編集しても同じ API を呼ぶ。これで逆編集が成り立つ（例：時間割の年間設定で曜日を変える → `weekday_swap` を保存 → 行事予定に「水曜授業」と出る。行事予定でそれを直す → 同じデータが変わる → 時間割にも出る）。
- 権限：行事予定か時間割のどちらかで Editor 以上なら編集できる。不在は本人が仮で登録でき、Editor が確定する。
- 記録：誰が、どのアプリから、いつ、何を変えたかを共通基盤に残す（`updated_by`・`updated_via`）。
- 同時編集：版番号（revision）による楽観ロックをかける。古い版のまま保存しようとしたら拒否し、最新の内容を返す。

### 3.2 変更の伝え方

- 共通基盤は、学校暦・共通マスタの変更ごとに**変更イベント**（school_id、種類、対象 ID、版番号、変更内容）を記録する（outbox）。
- 各アプリはイベントを受け取り、画面へは即時に知らせる（時間割には既存の WebSocket 通知がある）。
- 届かなかったときは再送する。同じイベントが二重に届いても結果が変わらないようにする（版番号で判定）。
- 片方のアプリが止まっていても、共通基盤への保存は成功する。止まっていた側は、再開したときに未処理のイベントを読む。

### 3.3 時間割での反映（連携4）

1. 学校暦の変更が届いたら、時間割は該当日のコマに**印**を付ける（行事で止まる／曜日の読み替え／不在で代講待ち）。この時点ではコマを書き換えない。
2. 時間割担当が、時間割の既存の流れ（下見 → 実行 → 取り消し：`event_apply_runs`）で確定する。確定した結果だけが、時間割の版（コマ・配置禁止・代講）に書き込まれる。
3. 学校暦のほうが後から変わったら、確定済みの反映との差を「要再確認」として出す。

行事予定側でも同じ考え方を取る。時間割から来た曜日の読み替えは表示するだけで、行事予定の固有データ（日次項目・当番）を自動では書き換えない。当番の競合は、その時点の不在から毎回導出する（DESIGN §4.7.2 のとおり）。

## 4. 画面（連携1）

- 時間割アプリの「行事予定」ボタンは削除する。
- 両方を契約している学校では、両アプリのヘッダーに**行事予定⇔時間割の切り替えスイッチ**を出す。切り替えても同じ日付・週を保ったまま開く（深いリンク）。
- 片方だけの契約ではスイッチを出さない。共通基盤の契約情報で判定する。
- 時間割だけを契約した学校は、行事・曜日の読み替え・不在を時間割の画面から入力する。保存先は同じ学校暦である。時間割側にも最小限の入力画面が要る。

## 5. 移行と解約

### 5.1 既存データの移行（連携6）

- 学校暦ができたら、時間割の既存データを学校ごとに一括で移す。対象は `annual_events`（行事）、行事由来の配置禁止の元データ、代講の不在情報。
- 学校ごとに「学校暦を読む方式」へ切り替える。不具合があれば、その学校だけ元に戻せるようにする。
- 時間割側の最優先ルール（v5 の完成を明示的に確認するまで、v4 の切り替えはしない）とは切り離して進める。時間割側の作業は、時間割の運用（Task の起票とレビュー）に従う。
- 行事予定の試作データ（予定・日レコード・祝日・人・時限）は、共通基盤の学校暦と共通マスタへ移す。

### 5.2 片方を解約したとき（連携7）

- 学校暦と共通マスタはそのまま残り、残った製品から使える。
- 解約した製品の固有データは、閲覧と書き出しだけができる状態で一定期間保管する。再契約すれば元に戻り、期間を過ぎたら削除する。期間の長さは、契約の設計で決める。
- 切り替えスイッチは消える。

## 6. DESIGN-AUTH-TENANCY.md への影響

- **共通基盤の範囲が広がる**：学校・利用者・役割・契約・年度・学期に加えて、学校暦と共通マスタを持つ。
- **行事予定の DB から外れるもの**：`events`・`event_assignees`・`event_targets`・`day_records`・`holidays`・`people`・`period_patterns`／`period_definitions`、学年・クラスの `targets`。これらは共通基盤へ移る。
- **行事予定の DB に残るもの**：`item_definitions`／`item_options`・`daily_values`・当番一式（`duty_*`・`rotation_members`）・`view_definitions`・`publications`・部活動などの対象軸・`school_settings`。DESIGN-AUTH-TENANCY §3 の school_id・`tenantDb`・分離テストは、残るテーブルに適用する。
- **公開範囲のフィルタ（§4.5）は共通基盤側でも必要になる**：行事の visibility、休暇分類の秘匿、職員以外に人名を返さないこと。共通基盤の API に同じ規則を実装する。行事予定アプリは、共通基盤から受け取ったものを、さらに自分のビューで絞る。
- **当番パネル**：不在は共通基盤から、当番は行事予定の DB から読んで、競合を導出する。

## 7. 次に決めること

1. 共通基盤の実装場所と技術（school-timetable と同じく Postgres＋tRPC にするか、独立したサービスにするか）。
2. 学校暦の API とイベントの形式（種類ごとの項目、版番号、再送の仕様）。
3. 時間割側の受け口（印の付け方、`event_apply_runs` との対応、代講待ちの作り方）。時間割側の Task として起票する。
4. 解約後の保管期間。
5. 試作（Hatch ランタイム）の段階で、どこまでを共通基盤の形に寄せて作っておくか。
